CHAPTER 07

工具设计与 ACI

像打磨 HCI 一样打磨 Agent-Computer Interface

工具是 Agent 与外部世界的契约。多数成功实现花在“优化工具”上的精力，不亚于优化整体提示词——因为 Agent 好不好，很大程度取决于它能否正确、高效地用对你的工具。

边界
职责单一、无歧义
如果连人类工程师都说不清某个场景该用哪个工具，就别指望模型能选对。工具之间应避免功能重叠。
文档
为“模型视角”而写
好的工具定义包含使用示例、边界情况、输入格式要求、与其他工具的清晰分界。像给团队里初级同事写一段极好的 docstring。
防错
Poka-yoke 防呆
改造参数，让“犯错”更难发生。例：把相对路径改为强制绝对路径后，模型使用近乎无误。
选择工具格式的经验法则
  • 给模型足够 token 去“思考”，别让它把自己写进死角
  • 让格式贴近模型在互联网上“自然见过”的形态
  • 避免格式“开销”：不用精确计数上千行、不用为写代码而转义字符串
  • 先直接 API 跑通，再考虑框架封装；工具需自包含、抗错误
MCP 让生态复用，但更要审视质量
Model Context Protocol 让你接入丰富的第三方工具生态。但当 Agent 遇到“没见过、描述质量参差不齐”的 MCP 工具时，坏描述会把它带进完全错误的死胡同。给 Agent 明确启发式：先盘点可用工具、按用户意图匹配、优先专用而非通用工具。

一个高杠杆技巧：让模型帮你改进工具。Claude 4 级别模型可以拿到“工具 + 失败模式”后诊断原因并重写描述。让“工具测试 Agent”反复试错几十次，把发现的坑写回描述——曾用此流程让后续 Agent 的任务完成时间下降约 40%。
