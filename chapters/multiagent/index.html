CHAPTER 11

多智能体系统

编排者-工作者，用并行把 token 花在刀刃上

Anthropic 的 Research 功能采用 orchestrator-worker（编排者-工作者）：一个 lead agent 规划并创建并行 subagents 分头搜索。内部评测中，“Opus 做 lead + Sonnet 做 subagent”的多智能体系统，比单 Opus 在研究评测上高出 90.2%。

为什么有效：本质是“花够 token”
在 BrowseComp 评测中，三个因素解释了 95% 的性能方差，其中 token 用量本身就解释 80%，另两个是工具调用次数与模型选择。多智能体通过“各自独立上下文窗口 + 并行推理”扩大了可用于问题求解的 token 总量。搜索的本质是压缩：子代理并行探索、把最重要的 token 蒸馏给 lead。
提示与协调的 8 条实战原则
  • 像你的 Agent 一样思考：用真实提示与工具做分步模拟，快速暴露失败模式
  • 教会编排者如何委派：每个子任务要有目标、输出格式、工具/来源指引与清晰边界，否则会重复劳动或留空白
  • 按查询复杂度分配算力：简单事实 1 个 agent 3–10 次调用；对比类 2–4 个 subagent；复杂研究 10+ 个各司其职
  • 工具设计与选择至关重要：坏描述会把 Agent 带进完全错误的死路，每个工具用途唯一、描述清晰
  • 让 Agent 自我改进：把“工具 + 失败模式”交给模型，让它诊断并重写描述
  • 先广后窄：像专业研究者一样先扫描全貌，再逐步聚焦，别一上来就长而具体的查询
  • 引导思考过程：用扩展思考做可控草稿纸，规划工具选择、复杂度与子代理数量
  • 并行工具调用：lead 并行拉起 3–5 个 subagent，subagent 内并行 3+ 工具，复杂查询耗时最多降 90%
涌现行为与协调复杂度
多智能体会有“未被编程却出现”的涌现行为：对 lead 的小改动会 unpredictably 改变 subagents 的表现。好的提示不是死规则，而是“协作框架”——定义分工、解题思路与算力预算。早期常见错误：为简单查询拉起 50 个子代理、无休止找“不存在的来源”。
