落地方法论：从工作流到自主 Agent

可组合的经典模式，按需逐级加复杂度

这些不是教条，而是生产中反复出现的“积木”。原则只有一条：先在最简单的方案上跑通，只有当复杂度能“被度量地”改善结果时，才叠加下一层。

1
Prompt Chaining（提示链）
把任务拆成固定顺序的多步，前一步输出喂给后一步，中间可加程序化“闸门”校验。适合能干净拆分成固定子任务的场景——用延迟换准确率。例：先写大纲 → 校验大纲 → 再基于大纲写正文。
2
Routing（路由）
先对输入分类，再分发到专门的后续流程 / 提示 / 模型。做好关注点分离，避免为某一类输入优化而伤害另一类。例：把“退款/技术问题/闲聊”分流；简单问题走便宜模型，难题走强模型。
3
Parallelization（并行化）
两种形态：分段(Sectioning)——把独立子任务并行跑；投票(Voting)——同一任务多跑几次取多样结果。例：一个实例回答、另一个实例做内容安全审查；多提示复查代码漏洞。
4
Orchestrator-Workers（编排者-工作者）
中心 LLM 动态拆解任务、分派给 worker LLM、再综合结果。与并行化的关键区别是“子任务不预定义”，由编排者按输入决定。例：一次改动多文件的编码任务、多源信息搜集。
5
Evaluator-Optimizer（评估者-优化者）
一个 LLM 生成，另一个 LLM 给出评估与反馈，循环迭代精修。适用于有清晰评估标准、且迭代能带来可度量价值的任务。类比人类写作的反复修改。
6
Autonomous Agent（自主代理）
本质就是“LLM 在循环里基于环境反馈使用工具”。适合无法预知步数、需要对决策有一定信任的开放问题。自主性带来更高成本与错误累积风险——务必在沙箱里大量测试并加护栏。
框架要用得明白
LangGraph、Claude Agent SDK、Rivet、Vellum 等能帮你快速起步，但也常常多包一层抽象，遮蔽底层提示与响应、增加调试难度。建议：先直接用 LLM API（很多模式几行代码就能实现）；若用框架，务必理解其底层代码——错误的“黑箱假设”是最常见的翻车来源。
